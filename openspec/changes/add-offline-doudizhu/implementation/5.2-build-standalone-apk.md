# Implementation Note: 5.2 构建新独立APK

**Task:** 5.2 in ../tasks.md

## Requirement and dependencies

依赖：5.1。对应 [android-installation](../specs/android-installation/spec.md) 的“独立运行核心游戏”和正式规格的“提供可安装 APK”。应用仍为原小游戏合集，而非另一个新EAS项目。

## Files and interfaces

修改实施时的 `app.json` 发布版本与Android versionCode，更新 `docs/doudizhu-validation.md`、`README.md` 的构建记录。复用 `eas.json` preview APK配置和现有包名／签名／项目关联；安装包产物按现有 `artifacts/` 惯例存放。

## Steps

1. 将 app.json、package.json 与锁文件的应用版本设为1.2.0，Android versionCode为4；保持包名com.seele.minigames和原签名，保留旧1.1.0 APK。
2. 确认5.1回归与expert对照通过，复用项目关联与本地签名，不创建新账号、项目或签名。
3. 用户于2026-10-21明确改为本地编译。使用 Expo prebuild 生成忽略的 Android 工程，以项目指定 Gradle 执行 `:app:assembleRelease`；SDK与Gradle缓存保存在本地验证目录。签名材料仅用于本地签署，置于忽略目录，不写入源码或日志。沿用原发布签名，避免升级时因签名不同而丢失覆盖安装能力。
4. 核验 APK 的独立 JS bundle、内置配乐内容哈希、ARM64、非debuggable、16KB对齐、包名、1.2.0/code4、证书与旧版一致，保存SHA-256和构建日志。本轮不发起云构建。
5. 把新APK和5.1清单交给5.3验收，保留用户原有旧APK记录。

## Verification

构建命令成功结束且得到可安装 `.apk`，版本正确、包名延续原项目。记录真实构建结果。Android导出或 `.aab` 不能替代APK，构建成功不等于手机离线、方向或存档已经通过。

## Risks or handoff notes

应用版本升级和新方向配置须重新构建。此任务不把正式规格同步／归档作为构建动作的一部分；完成状态只在tasks.md。
