# Implementation Note: 3.1 独立存档与重放校验

**Task:** 3.1 in ../tasks.md

## Requirement and dependencies

依赖：1.3。对应 [doudizhu-session](../specs/doudizhu-session/spec.md) 的“完整独立对局存档”“安全恢复与写入失败反馈”，场景“叫抢中退出并重进”“出牌中关闭重开”“快速操作和存档隔离”“损坏或旧版本存档”“存档写入失败及恢复”。

## Files and interfaces

新建 `src/features/doudizhu/storage.ts`、`storage.test.ts`、`saveQueue.ts`、`saveQueue.test.ts`。存储适配器保持可注入。新键为 `doudizhu.save.v1`，返回区分缺失、有效、无效或读取失败，供会话显示准确反馈。

## Steps

1. 写calling、grabbing、playing、finished的序列化往返案例，保存难度、初始发牌、动作及派生状态。
2. 从初始发牌和当前deal的initialRevision重放动作，验证规范化组合、角色、轮次、底牌加入、目标、不出数和结果与快照一致；加入全不叫重发后的保存／恢复案例；未知版本和非法动作拒绝恢复。
3. 按阶段验证54张唯一实体牌：叫抢时三人手牌＋底牌；出牌后当前手牌＋已出牌。公开底牌注释不重复计数。
4. 参照2048队列模式实现斗地主自有串行写入和读屏障，队列跨挂载共享，写入失败恢复链而保留失败反馈。
5. 用延迟写入测试旧快照不能覆盖新快照，最新成功状态可恢复；确保适配器只操作斗地主键。

## Verification

执行 `npm test -- --runInBand src/features/doudizhu/storage.test.ts src/features/doudizhu/saveQueue.test.ts`。预期三阶段及叫抢子阶段恢复一致；重复牌、未知版本、篡改历史被拒绝；读等待写入，失败后的新写入仍成功；2048键始终不变。

## Risks or handoff notes

缺失不是损坏。写入未完成即被强杀只能恢复上一份成功状态，不能在测试中伪称动作都已保存。日志上限校验须允许正常完整对局，但防止无界损坏数据导致重放卡顿。
