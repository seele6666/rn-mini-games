# Design

## 2026-10-22 体验升级设计（优先于下文旧三档说明）

- 新增Difficulty expert与searchProfiles，困难保留400节点/150ms；expert初始3200节点/800ms/80000工作单元、8候选/12采样/24深度。共享公平观察、8ms分片与取消，统一decision分派供电脑及提示使用；新档叫抢沿用当前策略。存档保持v1，难度白名单扩展，旧档恢复兼容。至少100种子×3座次、其他座位固定普通，对困难与专家成对比较，要求全部合法终局且专家总体胜局更多，失败保留继续调优。
- 最近三手从公开history筛选play后取末三条，实体牌通过canonical deck重建；三个等宽独立横向浏览区从左到右时间递增，展示玩家与牌型，右侧标最新。仅当前target有效时标记对应手待压。清轮保留历史，deal变更随引擎历史重置。800×360保持手牌116高及固定牌桌，中心改为状态行加三手牌区，不新增整页滚动。
- 使用SDK57匹配expo-audio/expo-haptics。配乐Monkeys Spinning Monkeys本地打包，来源https://incompetech.com/music/royalty-free/index.html?isrc=USUAN1400011 ，按作者页面CC BY署名并保存来源/许可证及转码说明。音乐循环、默认25%，前台且路由聚焦才播放；音频焦点丢失交由音频模式暂停，不与外部音频混播，失败显示重试入口。Web需用户交互再播放。播放器卸载释放，异步播放结果在失焦后不能重启。
- settings v1独立键doudizhu.settings.v1，字段musicEnabled/volume/hapticsEnabled默认true/.25/true，字段校验和损坏回退不影响game存档，保存串行避免乱序并反馈失败。UI设置面板打开以受控focused暂停现有session的AI和hint，关闭恢复原revision。
- 按下高亮/轻缩放、手牌选中动画与描边，触摸取消/滑动不触发haptics；selection/confirm/error三个反馈等级，节流与总开关。仅真人有效交互及非法提交反馈，禁用控件和电脑不触发。非法提交保留选择，提示立即显示计算中。
- 发布1.2.0/code4，沿用包名与原签名，本地ARM64构建，保存APK SHA及内置音频核验。综合测试重做；真机专家端到端p95≤1.2s与返回≤100ms、全部音乐/手势/存档/2048项目仍需实际设备，不以Node或Web替代。

## Context

现有首页、路由、2048 游戏逻辑分别在 `src/app/index.tsx`、`src/app/games/2048.tsx`、`src/features/game2048/`。首页及其测试固定为一个入口；`app.json` 全局 portrait，根 Stack 尚无页面方向。AsyncStorage 与串行存档队列已用于 2048，但现有 hook 没有后台电脑调度机制。

本变更采用 brainstorm 的已确认需求和固定规则版本。结算仅显示阵营与真人胜负。斗地主逻辑、存档和测试独立，保留 2048 的行为与存档格式。

## Goals and non-goals

- 完成完全离线的三人叫抢、出牌、两名公平电脑、三档策略、横屏交互和中途恢复。
- 规则与电脑决策可脱离 React 单独测试；生命周期与存档失败能够确定地复现。
- 本次不引入服务端、训练模型、金币、倍率积分或新的通用游戏框架。先沿用既有基础依赖。

## Architecture and data flow

### 模块边界

以下是实施阶段的新文件目标，不代表这些文件当前已经存在。

| 文件 | 职责与接口 |
|---|---|
| `src/features/doudizhu/types.ts` | 实体牌、座位、阶段、动作、难度、规则版本和会话类型 |
| `cards.ts`、`rules.ts` | 54张牌、带种子的洗牌、牌型解释、比较和结构化合法动作生成 |
| `engine.ts` | 纯状态机：`createGame`、`getLegalActions`、`applyAction`，拒绝非法和过时动作 |
| `ai/observation.ts` | 从完整状态提取指定座位可见的 `PlayerObservation`；唯一的AI输入入口 |
| `ai/heuristic.ts`、`ai/search.ts` | 简单／普通策略与受预算、可取消的困难推演 |
| `storage.ts`、`saveQueue.ts` | 斗地主独立版本化存档、重放校验、串行写入与读取屏障 |
| `useDoudizhu.ts` | 恢复、真人操作、提示、存档反馈、前后台和电脑任务生命周期 |
| `GameScreen.tsx`、`Hand.tsx` | 阶段界面、牌桌、选牌、结果、难度选择与重开确认 |
| `src/app/games/doudizhu.tsx` | 路由适配及无返回栈时的首页回退 |

数据流：

```text
UI action --> session --> pure engine --> new immutable state --> save queue
                  |                            |
                  |                            v
                  +<-- guarded AI result <-- observation --> policy/search
                                               |
initial deal + history --> replay validator --> restore
```

### 状态机与动作

- 阶段区分 `calling`、`grabbing`、`playing`、`finished`；难度选择、加载和确认弹窗是会话UI状态，不伪装成游戏回合。
- 完整状态包括 `gameId`、`dealId`、递增 `revision`、当前deal的 `initialRevision`、规则版本、难度、当前初始发牌、叫抢进度、角色、当前实体手牌、公开底牌、当前待压组合、最后有效出牌者、连续不出数、历史、结果。
- 动作区分叫、不叫、抢、不抢、出牌、不出，并带座位及期望的 `gameId/dealId/revision`。纯引擎检查阶段、轮到者、牌权、牌型与比较；拒绝时返回原因，状态保持不变。
- 所有人不叫时创建新的 `dealId`，洗发新牌并顺延起叫座位；只保留当前发牌的重放历史，旧叫抢决定不作用于新牌。新发牌快照保存此时的initialRevision，后续当前deal历史从该基线重放；revision跨deal继续递增，不能从0重建再误判存档。
- 地主确定后只加入一次底牌。普通有效出牌清零不出数；连续两次不出后目标清空，由最后有效出牌者领出。任意手牌清空立即进入 finished，不再调度下一人。
- 牌型判定返回所有合法解释。领出按主体长度降序、主体点数降序选择；跟牌先筛出匹配目标且能够压过的解释，再按主体点数降序选定。历史记录选定的规范化牌型，重放时重新判定并验证，不能信任存档自报的牌型。
- 合法动作按点数计数与主体／翼牌结构生成，不枚举手牌的所有子集；同点不同花色的等价选择用稳定实体ID取样去重。真人手动出牌仍完整判定，不受电脑候选截断影响。

### 电脑视角与三档策略

- UI和AI的可见模型与完整引擎状态分开。策略入口不得接收或持有真实对局的完整 `GameState`；其输入仅为自己手牌、公开底牌（叫抢阶段为空）、公开历史、角色／轮到者、余牌数、合法动作及注入的独立随机源。搜索执行层可以使用从观察采样构造的合成GameState调用引擎，但不能取得真实隐藏分配；每名模拟策略仍仅接收自身观察。
- 地主确定后，未知牌池从54张牌扣除自牌、公开已出牌及仍归地主的已知底牌；底牌是归属约束，不重复从牌池扣除。叫抢时未公开的3张底牌必须仍属于未知集合。
- 简单优先小牌和完整组合，在可接受候选内适度随机；普通先识别立即获胜，再比较拆牌成本、估计剩余手数、对手余牌威胁和农民队友接手机会。叫抢依据自己的高牌与组合评分，不能看底牌；困难叫抢可沿用普通评估。
- 困难出牌以普通评分筛出有限候选，对符合公开信息的未知牌分配采样，使用同一引擎模拟后续。模拟中的各座位也须用自己的观察决策，不能让模拟策略直接读取所有样本手牌。
- 模拟收益按阵营胜负计算；截断局面使用双方出完距离、控制牌及队友机会估值。不能把“不出”当作没有压牌能力的硬约束。
- 起始预算建议最多400个模拟动作节点、150ms总计算时间，每个工作片段最多约8ms后让出JS线程；候选生成、评分、采样与模拟都计入预算。参数是可调实施起点，不是已测得性能。
- 在计算开始前确定一个合法普通回退。循环检查时钟、节点预算与取消信号；任何失败都回退，领出不能回退为不出。不能只在一个长同步循环外包 `setTimeout`。
- 同一观察、随机种子、节点预算与测试时钟应得到同一结果。真实时间预算可能改变停止位置；确定性测试使用注入时钟及节点预算。
- 提示复用真人观察及当前难度的策略，仅返回建议牌或不出，不调用引擎提交动作。

### 存档与恢复

- 新键 `doudizhu.save.v1`，封套保存格式版本、规则版本和完整状态；不读写 `game2048.save.v1`。
- 每次成功转换后排队保存不可变快照。队列在模块层跨挂载共享，读取等待此前写入；失败恢复队列链，向会话报告保存失败，下一次有效保存重试最新完整状态。
- 保存当前初始17/17/17＋3底牌、起叫者、initialRevision以及当前deal所有有效动作，使恢复可以从正确revision基线重放并与保存的派生状态比较。底牌加入地主后的公开展示是注释：牌守恒统计只计算当前三人手牌和已出牌，不再次计算显示的底牌。
- 校验版本、54个实体ID唯一、阶段／角色／行动者、底牌公开状态、目标组合、不出计数、结果与动作重放一致。损坏或未知版本回到新局选择并提示；首次没有存档属于正常情况，不显示损坏警告。
- 写入失败保留内存状态，明确提示未保存。不能保证操作系统在尚未完成写入时强杀也能保存；重开只承诺恢复最新成功写入的完整状态。测试与真机记录区分已完成写入和待写窗口。
- 确认重开时先取消旧任务，再等待用户选难度，创建新 `gameId` 并经同一队列写入；新局提交前旧存档仍可恢复。取消确认不取消当前局或更改难度。

### 生命周期与唯一提交

- 用路由 focus 与 `AppState === active` 两个条件控制电脑和提示；恢复加载完成后才允许调度。
- 每个任务记录 `gameId/dealId/revision/seat` 和会话generation。页面失焦、后台、卸载或新局使generation失效并取消任务；计算返回时再次检查所有标识和行动者，匹配才提交。
- 一个回合只有一个待执行电脑任务；effect重跑、重复AppState事件或快速挂载不增加同回合提交次数。提示任务独立，不自动提交游戏动作。
- 页面在后台或首页不执行电脑，不因迟到结果推进状态。前台恢复若仍是电脑回合重新计算一次；若是finished则仅显示保存结果。

### 页面方向与交互

- 优先使用现有 Expo Router native stack 的 `Stack.Screen` orientation：首页和2048为 portrait，斗地主为 landscape。调整 `app.json` 全局方向为允许页面控制的 default，并显式指定页面方向，保持启动首页为竖屏。
- 此方案由已安装的 `react-native-screens` 驱动。依据[Expo官方按页面方向文档](https://docs.expo.dev/versions/latest/sdk/screen-orientation/#per-screen-orientation-with-expo-router)，本次不预设增加 `expo-screen-orientation`。若实际版本或设备证明需替代方案，先记录原因并更新设计与依赖任务，不能静默引入。
- 方向的验收以新独立APK为准，覆盖关闭系统自动旋转、系统返回、无历史直接进入、快速往返和后台恢复。Web只要求可渲染和回退，不把浏览器方向模拟当成Android通过。
- 牌桌为固定安全区布局，不沿用整个页面可滚动的2048结构。手牌最多20张，用重叠排布与独立横向浏览保证每张可达；选牌按实体ID，点按取消，手牌滑动不触发外层页面动作。
- 当前阶段、行动者与操作权限来自引擎。结果只显示真人及阵营胜负；等待真人时没有自动代打计时器。

## Decisions and alternatives

- 选择独立纯TS引擎＋策略，便于离线、测试与学习；Python研究仓库不直接作为RN依赖。
- 困难采用受限采样模拟，不承诺科研模型级牌力；神经网络转换与原生推理留作未来独立变更。
- 斗地主单独存档与会话，沿用已有队列模式；不抽象或重构已经验收的2048引擎与存档。
- 规范化牌型和动作重放比仅保存手牌更容易验证一致性；增加初始发牌与历史字段，但对单局54牌规模可控。

## Risks and mitigations

| 风险 | 应对 |
|---|---|
| 飞机、四带二误判或生成动作与验证器不一致 | 规则表驱动边界测试；生成的每个动作重新通过验证，歧义牌型稳定归一化 |
| 农民为了自己的牌量阻碍队友 | 固定战术局面测试，立即阵营胜利优先；按地主／农民座次分别统计对局 |
| 未知牌采样泄露真实分配 | 观察接口隔离、模拟玩家视角、置换隐藏分配不改变决定的测试 |
| 搜索卡住UI或参数增加反而更弱 | 全流程预算与分片、合法回退、设备响应测试及成对种子胜率对照 |
| 写入乱序、旧AI污染新局 | 串行快照写入、加载屏障、generation及revision校验 |
| 配置看似横屏但原生未生效 | 新APK真机验证，不以Web/Jest代替 |

## Verification approach

1. 规则、发牌、叫抢、出牌：纯单元测试覆盖规格案例及54牌守恒，随机合法轨迹无非法转换。
2. AI：所有难度都满足合法性与视角隔离；预算0、异常、取消均有正确回退；提示不改变状态。简单／普通／困难的策略分支和推演操作有独立证据。
3. 存档与会话：用注入存储、时钟、随机源和可控异步任务复现写入失败、重挂载、后台恢复、迟到提交与重开。
4. 对局质量：至少100个固定发牌种子、每个轮换三个座次，分别对照简单与普通、普通与困难，记录阵营胜率、非法动作、未结束局、搜索节点及耗时。目标为普通优于简单、困难不弱于普通；结果不支持时调参或扩大样本，不将未验证牌力描述为高手。固定节点基准不等于手机时间预算的性能结果。
5. 执行 `npm run typecheck`、`npm test -- --runInBand`；原有2048与首页回归全部通过。Android导出只检查打包，独立APK和真机验收分别记录。
6. 真机在飞行模式、关闭Metro和Expo Go时，三档各完成一局，并覆盖叫抢／出牌恢复、20牌操作、方向切换、后台唯一提交及搜索期间返回。困难计算目标为p95不超过500ms，正常设备负载下返回响应目标不超过100ms；实际数据在实施验收记录，未测不打勾。

## Open questions

剩余仅为不改变规格的调优项：颜色、头像、布局尺寸、随机策略权重和预算参数。用户若改变叫抢或带牌细则，须先更新本变更的规格与相应任务，而不是在实现时自行决定另一个规则版本。
